I built a RAG pipeline from scratch on my laptop, one layer at a time, and measured every layer.

Some layers helped. One made results worse. And my favourite metric was hiding a bug.

Setup: 26 lecture-note files + 3 arXiv papers (3,017 chunks). Llama 3.1 8B + nomic-embed-text on Ollama, Qdrant, SQLite for keyword search, M4 Max. No framework. Eval: 24 questions + 4 off-topic ones.

Phase 0: Tracing first
Every request writes a trace with a hash of the config. Every number below comes from those traces.

Phase 1: Ingestion
Only new or changed files get re-embedded. A second run embeds 0 chunks. Embedding = ~88% of ingest time.

Phase 2: Vector + keyword search, merged (RRF)
hit@5: vector 0.79, keyword 0.92, hybrid 0.88.
Surprise: hybrid was worse than keyword alone. The embedding model blurs acronyms (RRF, SSE), so vector search dragged good keyword results down.
I also found mistakes in my own eval labels. Check labels before trusting scores.

Phase 3: Re-ranker (cross-encoder)
hit@5 0.96, a tie with keyword search. "What is RRF?" jumped from rank 12 to 1, but it missed one plain-English question.
Why keep it? Its score is the only one that separates real questions from off-topic ones. That gives a "not found" check: 4/4 off-topic questions refused, with no LLM call. Cost: ~45 ms.

Phase 4: Answers with citations
Off-topic refused 4/4. Real questions wrongly refused 1/24. 96% of answers cite a source, 0 fake citations.
First token in 1.7 s, ~14 ms per token after that, 3.5 s per question.
Ollama decodes at ~87 tokens/s. Memory bandwidth caps this model at ~110 on this chip, so decode is already near its limit.

What the answer eval caught:
1. My retrieval metric lied. "What is PagedAttention?" counted as a hit because the right FILE came back, but no chunk explained it. The LLM correctly said "not found". Keyword search matched "problem" and "solve", and the paper title in every chunk made "PagedAttention" look common.
2. Citations show where a claim came from, not whether it is true. Llama 8B once said GQA makes the KV cache "constant".
3. Laptop timing is noisy. One run was 3x slower with identical answers (macOS background jobs). Repeat before trusting a speed number.

Next:
- Fix that keyword bug and score chunks, not just files
- More off-topic questions + an LLM judge for "is it true?"
- Speed work, one change at a time: prefix caching, parallel requests, chunked prefill, flash attention, speculative decoding with a 1B draft model, Q8 vs Q4, quantized KV cache. PagedAttention and split prefill/decode need NVIDIA GPUs, so those move to the cloud.

Biggest lesson: measure each layer on its own. "Add hybrid search and a re-ranker" is common advice. On my data, one hurt, and the other mostly helped with saying "I don't know".
